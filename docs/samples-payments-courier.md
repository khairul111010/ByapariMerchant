# Real samples: payments, advance payments, courier, invoice, push

Generated by running the real API against a throwaway database with **fake** data. Same conventions as `samples.md`: money is a string, timestamps are ISO-8601 UTC.

## Values
- `payment.method` / `advance_payments[].method`: advance payments accept `manual_bkash | manual_nagad | cash`. The order's own `payment` row is `manual_bkash | manual_nagad | sslcommerz`.
- `payment.status`: `pending | paid | failed`. Verify sets it to `paid` (and the order's `payment_status` to `paid`); reject sets `failed`.
- `courier.booking.status` is whatever the courier reports (`in_review`, `delivered`, ...). Treat it as a free-form string and show it as-is. Raw courier responses are never returned.
- `courier.available_drivers` = drivers the plan allows **and** that have credentials saved. An empty list means: send the merchant to Settings > Couriers.
- The order's `amount_due` already subtracts paid advances. It is `0.00` once the order's own payment is `paid`.

## Rules the app must follow
- **Verify / reject** only make sense when `order.payment` is not null and `payment.status == "pending"`. There is no body. Both return the full order (`data`).
- **Advance payment**: `amount` must be > 0 and <= `amount_due`, otherwise `422` with `errors.amount`. Returns the full order.
- **Courier booking** refusals (always read `code`): `order_pending` (confirm the order first), `already_booked`, `driver_unavailable`. A failure from the courier itself is `422` with `code: "courier_failed"` and the courier's message. Offer a retry; nothing is saved on failure.
- **Reopening** a cancelled order can fail with `409 insufficient_stock` (shape below).

## FCM push + deep link (what the server sends)
Sent when a new order is placed, to every phone registered via `POST /devices`. The server never puts a customer name, phone or address in it.

```json
{
  "message": {
    "token": "<device token>",
    "notification": { "title": "New order ORD-000123", "body": "৳1,560 · Cash on delivery" },
    "data": { "type": "new_order", "order_id": "42", "order_number": "ORD-000123" },
    "android": { "priority": "HIGH", "notification": { "channel_id": "orders", "sound": "default" } },
    "apns": { "payload": { "aps": { "sound": "default" } } }
  }
}
```
- `data` values are always **strings** (FCM requirement): parse `order_id` to a number.
- Body for manual payments reads `bKash — verify payment` / `Nagad — verify payment` instead of `Cash on delivery`; online-paid orders read `Paid online`.
- Deep link: on tap, open the order screen for `data.order_id` and load `GET /orders/{id}`. The app must create the Android channel `orders` itself before the first push.
- Only `new_order` exists today. Ignore unknown `data.type` values instead of crashing, so future types are safe.

## Offline queue (app-side; what the server guarantees)
There is no server-side queue API. Which writes are safe to queue and replay:

| Safe to replay later | Why |
|---|---|
| `PUT /orders/{id}/status` | Setting the same status twice is a no-op (`409 insufficient_stock` is a real refusal: drop the job and tell the user). |
| `POST .../variants/{id}/stock` with `mode: delta` | Atomic, but **not idempotent**: replaying twice adds twice. Send once, mark the job done only on a response; on a network timeout, re-read the stock before retrying. |
| `PUT /orders/{id}/payment/verify` and `/reject` | Idempotent. |
| `DELETE /devices` | Idempotent. |

Do **not** queue: `mode: set` stock-takes (they need `expected`), advance payments (replay would record the payment twice), courier booking (`already_booked`), POS sales (stock is taken at once), deletes, and anything that creates a record.
